Foundations

_Choose the right mechanism

Most failures begin before the first tool call: policy, know-how, execution, and evidence are placed in the wrong layer.

Use this divider to reset attention. The next slides are about mechanism selection, not product features.
TT PSC

_The agent system, layer by layer

Specification What outcome is expected?
Project instructions What must every task know?
Skills How is a conditional workflow performed?
Agent / subagent Who owns the bounded task?
Tools and MCP Which actions and external systems exist?
Hooks · permissions · CI What is deterministically enforced?
Ask: where would you put “never deploy without approval”? Guidance belongs in instructions; enforcement belongs in permissions/hooks/CI.
TT PSC

_Six distinctions that prevent drift

Skill ≠ agent

A skill packages know-how. An agent owns a bounded task in an execution loop.

Instruction ≠ enforcement

Prose guides. Sandboxes, hooks, CI, and permissions can block.

Tool ≠ workflow

A compiler can act. A skill decides when, how, and what the result proves.

Prompt ≠ specification

A prompt starts a conversation. A spec is versioned, testable, and reviewable.

Plan ≠ approval

A plausible implementation path does not authorize product edits or release.

Command output ≠ evidence

Evidence adds environment, criterion mapping, result, and residual risk.

Invite one example from each team where these were confused in a real workflow.

Execution environments

_“Local” is not one thing

Separate where the user controls the task, where tools execute, and where the model reasons.

This distinction is the foundation for the threat-model exercise.
TT PSC

_Three planes, three different answers

1

Control plane

Where the user starts, watches, approves, and steers the task.

2

Execution plane

Where shell commands run and which checkout or filesystem changes.

3

Model plane

Where inference processes prompts and selected tool context.

Key insight: local code execution can still use a hosted model; a browser UI can still control a local session.
Ask participants to classify their current setup using all three planes.

_Choose execution mode from constraints

Choose local

Uncommitted changes, proprietary compiler, hardware/device access, private local services.

Choose worktree

Local tool fidelity plus isolation from concurrent tasks and experimental edits.

Choose cloud

Reproducible clone, scoped secrets, controlled network, background parallelism.

_Acceptance criteria must be falsifiable

Weak

“Parser handles invalid data.”

No boundary, observable result, state effect, or verification path.

Testable

Truncated record criterion

Given a length larger than the remaining buffer, return ErrTruncated, consume no next record, and perform no out-of-bounds read.

Describe behavior first. Implementation belongs in the plan unless it is a real compatibility or architecture constraint.
Have teams rewrite one vague requirement from their own backlog into a falsifiable criterion.

_Anatomy of a high-value skill

skill-name/ ├── SKILL.md │ ├── name + description │ ├── core workflow │ └── non-obvious invariants ├── references/ │ └── conditional command cards ├── scripts/ │ └── deterministic helpers ├── assets/ └── agents/openai.yaml
1Trigger: precise description and exclusions.
2Core: stable decisions that apply across repositories.
3Conditional detail: loaded only when needed.
4Evidence: exact reporting expectations.
5Tests: selection, non-selection, and failure paths.
A command catalog alone is not a skill. The value is knowing what to inspect, what to preserve, and what a result proves.

_Team A — gcc-dev decision points

Discover

C or C++? Make, CMake, Ninja? Compiler version? Build type? Test runner?

Preserve

Language standard, ABI/API, architecture, existing warnings, separate build trees.

Verify

Focused test, broader suite, ASan/UBSan, optional Valgrind/GDB, exact omissions.

Use gcc-dev. Diagnose the first actionable GCC error. Do not change the C++ standard or add warning suppressions. Report the exact build and validation commands.
Non-selection test: a Go REST endpoint prompt must not activate gcc-dev.
TT PSC

_Team B — mscpp-dev decision points

Discover

Developer PowerShell? Solution or generated project? Toolset, SDK, config, platform?

Preserve

Debug|x64, /MD-family consistency, ABI, calling convention, character set.

Verify

Focused project/test, documented suite, supported diagnostics, environment disclosure.

Use mscpp-dev. Build only WidgetTests from Product.sln for Debug|x64, run focused tests, and report the MSVC environment and every command.
Watch for mechanical GCC-to-MSVC flag translation and fixed personal Visual Studio paths.
TT PSC

_Team C — go-dev decision points

Discover

go.mod/go.work, Go version, packages, build tags, task runner, CI?

Preserve

Cancellation, timeout, error wrapping, goroutine ownership, generated-code policy.

Verify

Focused test, go test ./..., vet, race when supported, dependency diff.

Use go-dev. Fix the goroutine leak in TestShutdown. Preserve cancellation semantics, run the focused test first, and disclose every check the environment cannot run.

_Evidence and the release-ready decision

Criteria

Every acceptance criterion has a result.

Commands

Exact build and test commands are recorded.

Results

Pass, Fail, Blocked, or Not run.

Toolchain

Compiler, configuration, and limits are visible.

Deviations

Plan changes and reasons are explicit.

Risk

Residual risk is named, not hidden.

Review

Independent findings are resolved or accepted.

Authority

The agent stops before merge or release.

Decision: Release-ready only when evidence supports the contract. Otherwise record Not-ready and the missing proof.
Do not reward confident prose. Ask another team to reproduce one check from the evidence record.

_Watch for these misconceptions

“The UI tells me where code ran.”

Separate control plane, execution plane, and data plane.

“Local execution means no data leaves.”

Model inference or external tools may still cross a boundary.

“A skill is a security control.”

It guides behavior. Permissions, isolation, hooks, and CI enforce.

“Cloud is less safe by definition.”

Risk depends on identity, retention, isolation, secrets, and governance.

“The agent can approve its own gate.”

Human authority cannot be fabricated or inferred.

“Planned tests are evidence.”

Only observed results are Pass. Everything else is Not run or Blocked.

Run this as a challenge round. Read a statement and ask teams to correct it in one sentence.
